# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

## Product-specific design decisions

- The interface is Simplified Chinese and stays compact without using micro typography or exposing every secondary detail by default.
- Use warm neutral surfaces with deep teal only for actions and state emphasis.
- Avoid hero layouts, oversized type, giant cards, dashboard metrics, and decorative empty space.
- The desktop source of truth is a 1440 × 1024 three-column project workflow workspace: projects and runs, one current artifact or action, and evidence/context.
- Provider switching and Skill package management may borrow PI WEB's compact control-plane behavior, but the first prototype stays local and does not collect API keys or run remote installs.

## Validated product direction (2026-07-22)

- Pi Agent is a project-centered personal workflow player: the product centers long-lived projects, while a workflow engine repeatedly advances them and preserves state.
- Treat the project as the user-facing primary object, a workflow as a reusable method, a run as one execution, a conversation as the intervention surface, a Skill as a method used by a step, and a tool or script as the concrete action.
- Codex is the workflow factory and repair shop for open-ended creation, modification, and recovery. Pi Agent is the lightweight player for bounded, validated, recurring workflows. Do not position the difference as model choice or code versus content.
- V1 should prove one complete workflow, not a generic workflow marketplace or a broad personal-AI operating system.
- Build and validate the clickable frontend workflow before wiring real services. Treat its buttons, states, inline confirmation, and failure-recovery path as the implementation contract; replace fixtures incrementally instead of redesigning the flow in the backend phase.
- The first workflow is `weekly source monitoring -> candidate filtering -> five-minute guide -> user-selected staged close reading -> Zotero/Obsidian archival -> proposed project-state update`.
- Deterministic scripts handle collection, cursors, normalization, deduplication, rule filtering, and simple heat signals. AI handles semantic relevance, final selection, explanation, close reading, and proposed project implications.
- Each weekly run attempts all 11 registered sources and preserves per-source success, failure, and cursor state. Only papers published in the current weekly window count as new. If fewer than five qualify, fill the remaining slots from a stable classic-paper pool; if none qualify, return five classics. Label every classic `经典回顾 · 非本周新论文`, and label older first discoveries as `本周补发现 · 非本周新论文`.
- Candidate review provides an explicit `换一批推荐` action in place of the old run-level `重新准备全文` action. Each click preserves the Run and prior exposure history, first rotates to unseen eligible candidates, then fills from a cursor-paged pool of high-citation papers in registered venues: project-topic matches come first, followed by broader AI/ML field matches. Only report exhaustion after the source cursor is actually exhausted. Newly surfaced metadata is translated with the fixed GPT-5.3 Codex Spark profile, and rotation never prepares full text automatically; full-text retry remains a per-paper action.
- After semantic ranking chooses the final five candidates, download and submit all five PDFs to MinerU Cloud before review, using the daily free quota when available. This does not change the later close-reading limit: the user still selects at most two papers for staged close reading.
- Use MinerU Cloud v4 precision parsing only in V1. Its API token stays server-side in `.env.local`; partial uploads, quota exhaustion, per-paper failures, and resumable batch polling must remain visible rather than being collapsed into one generic error.
- A run prepares on schedule and waits for review. Project-scoped reads are allowed by default; every external or project write requires an exact preview and explicit confirmation. The user may select individual changes and confirm the selected batch once, with confirmations shown inline rather than in a persistent queue.
- A human-readable Markdown project-state file is the source of truth. Pi Agent's database is only an index, cache, and run-history store.
- Zotero owns bibliographic records, PDFs, the five-minute guide, and a link to the full note. Obsidian owns the canonical close-reading note. The project-state file stores only confirmed project implications, decisions, open questions, next actions, and citations.
- MinerU pre-parsing all five candidates does not authorize or imply Zotero archival. Only papers the user explicitly chooses as `collect` or `read` may enter a Zotero write proposal, and they are written only after the final exact preview is approved.
- In V1, an exact pre-existing Zotero item is a blocked, non-actionable `manual_update_required` proposal. The preview must say that Pi Agent will not move it to the selected collection or modify its PDF or note; do not present the run as fully archived until a separate supported update path exists.
- Close reading covers `research question`, `method/mechanism`, `experimental evidence`, and `project relationship`, but these are optional reading lenses rather than locked navigation gates. The first three may be used in any order; project relationship is synthesized after the other three. Together they produce one evolving Obsidian note per paper; weekly reports are indexes rather than mixed multi-paper notes. Obsidian writes still require a displayed write preview and explicit approval.
- Five-minute guides are human-facing Chinese artifacts: `problem`, `why_read`, `intuition`, `evidence`, `limitations`, and every follow-up question must use Simplified Chinese while preserving necessary English technical terms.
- Keep paper content in two representations: AI receives the lossless MinerU Markdown, while human reading surfaces render sanitized document structure and LaTeX. Any selectable rendered view must preserve a verified mapping back to the canonical source offsets used by Agent citations.
- The web app is the active reading workspace. Continuous structured text is the center/default reading surface, paragraph focus is an optional mode, and the original PDF remains directly available. Show original text separately from AI explanation, keep stable paragraph anchors, and do not claim a PDF page mapping unless one actually exists.
- Opening a selected paper enters the paper workbench directly, and reopening it resumes at the last saved paragraph without an intermediate status or “continue” page. The five-minute guide is a collapsible orientation section inside that workbench rather than a separate required page.
- The right rail has one full-height persistent paper-level Agent conversation surface plus separate reading-notes and project-context views. Full text never occupies the right rail. Selecting text in the center adds a removable citation context to the Agent composer only; it must not show a floating `Ask AI` or `Translate` menu and must not call a model until the user submits a question. Translation and explanation are ordinary Agent requests, not separate tools.
- Paper Agent messages use paper-only context by default. Adding the project-state Markdown is an explicit, visible per-message choice so ordinary explanation and translation do not silently spend project-context tokens.
- The model selected inside the Paper Agent composer applies to that conversation only and is recorded per turn; changing it must not silently change the model used by later workflow stages.
- Paper Agent turns are independent from staged workflow outputs and archival state. Every turn records its provider, model, and source citations, but it does not advance a reading stage or enter Zotero, Obsidian, or project state unless a later workflow step explicitly proposes and confirms that write.
- `project_state.md` is the canonical structured project-state source for the first real project. The right rail, candidate ranking, project-aware Agent turns, project-relation stage, and project-state preview must all read that same server-side Markdown revision; live runs must never silently fall back to fixture project state.
- An answered Paper Agent turn may deterministically produce one inline Obsidian note-change proposal without a second model call. The proposal must show the server-derived target path and exact diff, and it may write only after an explicit hash-bound confirmation. Abandon, conflict, approval, write, and read-back verification are durable paper-level Agent-action states and must not change the Run phase, reading status, current stage, or stage artifacts.
- Canonical Obsidian paper notes use one stable paper-identity marker plus separate managed `workflow` and `agent-notes` regions. Agent actions append stable marked blocks only inside `agent-notes`; the later four-stage whole-note preview may replace the workflow region only while preserving confirmed Agent blocks exactly. Unmanaged or identity-mismatched existing files are never overwritten.
- Do not live-sync paragraph questions, highlights, or reading position into Zotero in V1. Pi Agent owns in-progress reading state; Zotero receives the confirmed bibliographic record, original PDF, five-minute guide, and Obsidian link; Obsidian receives the durable close-reading note.
- Five-minute guides are paper-neutral: use only bounded parsed-paper blocks, never project context; emit the fixed five sections, 2–3 questions, and verified block references. Keep project impact as a separately labeled candidate-stage judgment based on metadata and abstract evidence.

## Model integration decisions (2026-07-23)

- Model credentials live only in the loopback Node.js service environment; never expose them to browser code or persist them in frontend settings.
- Keep raw paper metadata and abstracts immutable. AI-generated `selection summary` and `project impact` are separate display artifacts with their own source, model, prompt version, input hash, usage, and audit record.
- Candidate-summary calls use an explicit fixture fallback, input-hash cache, and in-flight deduplication. Page load, reload, provider switching, and model switching must not call a paid model; only an explicit user action may refresh candidate explanations.
- `codex-subscription` means the local official Codex CLI reusing its own ChatGPT subscription login. Never read `auth.json`, copy OAuth tokens, fall back to an OpenAI API key, or describe this path as the Responses API.
- The Codex subscription adapter must remain ephemeral, schema-constrained, non-interactive, and tool-free: ignore user config and rules, disable shell/unified exec/web/apps/plugins/multi-agent tools, and run from an empty temporary directory.
- DeepSeek uses only the dedicated server-side `PI_DEEPSEEK_API_KEY` and the official Chat Completions endpoint. The V1 allowlist is `deepseek-v4-pro` and `deepseek-v4-flash`; do not reintroduce deprecated `deepseek-chat` or `deepseek-reasoner` defaults.
- Keep the model layer Pi-style and thin: one bounded structured call per semantic step, short versioned prompts loaded on demand, only stage-relevant context, strict schemas, and deterministic script fallbacks. Do not embed the full Pi coding-agent runtime in this workflow player.
- Treat incomplete, failed, filtered, refused, empty, malformed, and unknown-paper outputs as failures; never cache them. Cache read/write failures must fail open without discarding a valid paid result or triggering an immediate duplicate call.
- A paper is selectable only when the current build has a valid downstream guide contract for it. Do not allow a UI choice that can advance into an empty guide or reading state.

## Guided-reading redesign (2026-07-24, confirmed after competitive research)

- Confirmed after researching Semantic Reader/Scim, Explainpaper, SciSpace Copilot, SocratiQ, and NotebookLM: guided reading is `orientation first -> point-of-need teaching`, not a forced sequential paragraph/section conveyor. This adjusts the earlier "Default close reading is Agent-led paragraph walking" default: sequential walking becomes one optional convenience, not the default rhythm.
- Orientation layer: opening a paper still gives a whole-paper map (what it solves, the route, the 2–3 spots most worth reading, what to stay skeptical about). This is the existing overview, strengthened; a future enhancement may mark those must-read spots inline in the right-side original text (Scim-style), but never force reading order.
- Point-of-need teaching is the main interaction: the reader clicks any section, or selects any span, and the Agent teaches that spot. Depth is user-adjustable (e.g. 小白 / 一般 / 进阶) and every explanation is re-runnable on the same spot (换个说法再讲 / 多打比方 / 再浅一点) to reinforce memory. Depth level is a system-prompt variant, kept per turn; it must not silently change later workflow-stage models.
- Section granularity must be real top-level chapters: skip front-matter/author/affiliation blocks as a walkable "section", and do not fragment into dozens of tiny path-based buckets. A section walk that lands on cover/author material with no teachable body is a bug.
- Jargon is the core novice need and uses BOTH representations: (1) inline — each teaching answer marks key terms with a one-line plain-language gloss without breaking reading flow; and (2) a per-section/per-answer term list that can be reopened and re-explained repeatedly. Terms remain re-askable to deepen memory.
- Reinforcement via optional self-check: after a section, the reader may request 2–3 comprehension questions (SocratiQ-style) generated only from the bounded parsed-paper content. Self-check is opt-in, never blocks reading, and is not an archival/reading-stage advance.
- Translation and "explain simpler" stay ordinary Agent requests (per the Agent-center rules), but a one-tap 翻译这段/这节 shortcut may prefill such a request; it still requires explicit submit and never auto-calls a model on open/select.
- Notes follow pin-as-you-go + archival synthesis: during reading, confirmed conclusions can be pinned to the right-side reading-notes artifact (lightweight, optional, anytime); the single complete note is composed once at archival time from the pinned points plus four-lens coverage, then shown for hash-bound confirmation. Do not force per-section note-writing.
- The reading workbench must surface a `从导读重新开始` restart control (the existing `restartJournalReadingFromGuide` path) with its exact-confirmation dialog; it preserves candidates/parsed full text/guides, clears only unfinished reading/Agent state, and stays blocked after any archival preview, external write, or committed Agent note. It was missing from the Agent-center workbench top bar and must be restored there.
- Center Agent conversation is now the primary working/teaching surface, so its working text should read comfortably (≥13–14 px on desktop), not sit at the 12–13 px floor used for secondary rails.
- Right-side original text must render the paper's figures and tables (not only text/math); a reading surface that silently drops figures/tables is incomplete. If parsed data does not retain them, that is a parsing/data gap to fix rather than a rendering choice.

# Agent 运行复盘

把复盘当作手动或低频触发的观察层。先从真实历史证据建立基线，再提出改进；不要进入运行时底盘。

## 边界

- 默认只读。不得修改代码、提示词、Skill、设置、数据、Git 或外部系统。
- 不启动新的项目任务，不调用外部连接器，不发送通知，不创建后台监控。
- 不把一次异常概括成系统规律；证据不足时标记 `未知`。
- 隐去密钥、绝对路径、私人内容和模型私有推理，只引用安全的公开活动、状态、用量、验证与用户反馈。
- 若用户随后要落实改进，结束本 Skill，并把建议交回正常工作流程单独审阅、实施和验证。

## 工作流

1. 明确复盘窗口：时间范围、项目或会话范围、是否有上一期报告。用户未指定时，选择当前项目最近一段可审计历史，并说明样本边界。
2. 读取最少必要证据：终态、公开进度、工具与运行结果、重试、等待用户、停止、失败、验证、用量、用户纠正和已确认改动。不要批量读取与复盘问题无关的正文。
3. 建立事实基线：统计完成、失败、停止、等待、返工、重复工具、验证通过率、耗时或用量。缺失字段不推断。
4. 聚类重复模式：只保留至少两次出现，或一次但影响重大的问题。每个结论绑定次数、样本和可核对证据。
5. 提出最小改进：区分确定性脚本、Prompt/Skill、工作流、界面或运行环境问题；写明预期影响、风险和下一期观测指标。
6. 若存在上一期报告，按同一口径比较 `改善 / 持平 / 退化 / 未知`。口径变化时禁止给出伪趋势。
7. 在对话中输出报告。只有用户另行明确要求保存时，才进入正常工作的文件预览与确认流程。

## 报告合同

按下列顺序输出：

1. `范围与证据`：窗口、样本数、来源和缺口。
2. `本期闭环判断`：一句话结论，标明置信度。
3. `反复模式`：问题、证据、影响、可能原因；区分事实与推断。
4. `改进建议`：最多五项，按收益与成本排序；每项给出可验证指标。
5. `前后比较`：仅在存在可比基线时给出趋势。
6. `下次观察`：建议的复盘时间或样本阈值，以及需要继续收集的证据。

保持归纳性和可审计性。不要输出运行时架构重写方案，除非历史证据明确表明局部改进无法解决问题。
